# Дизайн: обучение LLM проактивной агентности для управления вербальным роботом

**Дата:** 2026-08-12
**Автор:** Сундетов Т.
**Диссертационная тема:** Исследование и разработка информационных моделей и технологии создания вербального робота
**Статус:** согласован, готов к переходу в план работ

---

## 1. Контекст

Существует рабочий прототип вербального робота. Текущий контур:

```
User → Query → [Микрофон → Whisper → текст]  ┐
              [Камера   → FaceID (DeepFace/dlib)] ┴→ LLM engine (облачная, по API)
                                                       ├→ Hard commands → серво
                                                       └→ Generate answer → Piper TTS → динамик
```

LLM в этой схеме выступает оркестратором на промпте. Система работоспособна и служит **бейзлайном**.

### Выявленные проблемы текущей системы

1. **Ошибки в командах** — модель порождает невалидный JSON, несуществующие действия, углы вне диапазона серво.
2. **Стоимость и зависимость от интернета** — оплата токенов, неработоспособность без сети, передача аудио и видео вовне.
3. **Отсутствие памяти и контекста** — робот не помнит конкретного человека, не связывает видимое со слышимым.
4. **Реактивность** (выявлено в ходе анализа) — вся схема запускается стрелкой `Query`, то есть только по обращению человека. Робот не является агентом.

## 3. Научная постановка

**Цель:** разработать информационные модели и метод обучения компактной языковой модели проактивному управлению вербальным роботом, обеспечивающий адаптацию в процессе эксплуатации без ручной разметки и без потери речевых способностей модели.

### Задачи

1. Анализ существующих информационных моделей и архитектур управления роботами на основе LLM; выявление ограничений реактивной парадигмы.
2. Разработка информационной модели ситуации — единого представления мультимодального потока восприятия.
3. Разработка информационной модели поведения — политики выбора момента и типа воздействия `ACT / WAIT / OBSERVE`.
4. Разработка информационной модели персонифицированной памяти.
5. Разработка информационной модели неявной обратной связи — представления реакции человека как оценочного сигнала.
6. Разработка технологии обучения: двухконтурная архитектура, гарантированная валидация команд, дообучение адаптера без деградации речи.
7. Экспериментальная проверка на физическом прототипе, оценка вклада каждого компонента.

### Научная новизна

1. **Информационная модель ситуации и поведения вербального робота**, формализующая взаимодействие как непрерывный процесс принятия решений на потоке восприятия с обучаемым выбором момента вмешательства — в отличие от существующих моделей, инициируемых обращением человека.
2. **Информационная модель неявной обратной связи**, представляющая невербальную реакцию человека на действие робота как оценочный сигнал, что позволяет адаптировать робота в эксплуатации без участия разметчиков.
3. **Технология специализации языковой модели под воплощённую агентность** на основе двухконтурной архитектуры, сохраняющая речевые способности; количественное измерение соответствующего компромисса.
4. **Методика приведения разнородных HRI-корпусов к единой информационной модели ситуации** и система метрик проактивной агентности.

### Положения, выносимые на защиту

1. Информационные модели ситуации, поведения и памяти вербального робота.
2. Метод неявной награды и метод дообучения на её основе.
3. Двухконтурная архитектура локального контроллера с гарантированно валидными действиями.
4. Результаты исследования компромисса «агентность — сохранение речевых способностей» и метод его контроля.

## 4. Архитектура

### 4.1. Двухконтурная схема

```
   Восприятие ──→ ┌──────────────────────────────┐
   (речь, FaceID, │  КОНТУР РЕШЕНИЙ  (обучаемый) │──→ команды на серво
    визуальный    │  Qwen3-8B + LoRA "решения"   │
    контекст,     │  когда действовать?          │──→ "надо сказать вот это"
    память)       │  что сделать? что запомнить? │           │
                  └──────────────┬───────────────┘           │
                                 │                           ▼
                                 │              ┌────────────────────────┐
                                 └─────────────→│  РЕЧЕВОЙ КОНТУР        │──→ речь
                                                │  Qwen3-8B без адаптера │
                                                │  (веса заморожены)     │
                                                └────────────────────────┘
```

**Ключевое решение:** базовые веса модели не изменяются никогда. Обучается только LoRA-адаптер. Речевой контур — это та же базовая модель с **отключённым** адаптером.

Обоснование: катастрофическое забывание при узком дообучении — реальный измеримый эффект. Разделение контуров делает деградацию речи структурно невозможной, поскольку речевой контур не участвует в обучении. Для темы «вербальный робот» сохранение речевых способностей является не пожеланием, а условием выполнения работы.

### 4.2. Обоснование выбора базовой модели

**Qwen3-8B**, лицензия Apache 2.0.

| Критерий | Обоснование |
|---|---|
| Tool-calling и структурный вывод | лучший результат в своём классе размеров |
| Русский язык | сильный из коробки |
| Лицензия | Apache 2.0, ограничений на исследование и публикацию нет |
| Размер | помещается на доступном GPU вместе с адаптером |

Дополнительно обучается **Qwen3-4B** с тем же адаптером — как вторая точка на кривой «размер / качество / задержка» для главы с результатами.

Известное ограничение: слабая поддержка казахского языка. Вынесено за границы текущего этапа; решается отдельным языковым LoRA-адаптером на той же базе (vLLM поддерживает несколько адаптеров на одной базе).

### 4.3. Гарантия валидности команд

Валидность обеспечивается **грамматикой на уровне декодирования** (structured output / GBNF), а не обучением. Невалидный JSON или значение вне диапазона серво становятся непредставимыми на уровне выбора токена, независимо от качества обучения адаптера.

Это прямое решение проблемы 1 из раздела 1, причём с гарантией, а не с вероятностью.

## 5. Информационные модели

### 5.1. Модель ситуации (вход)

```json
{
  "time": "14:32",
  "silence_sec": 0,
  "person": {
    "id": "u_017",
    "name": "Айгерим",
    "known": true,
    "last_seen": "3 дня назад"
  },
  "visual": {
    "faces": 1,
    "distance": "близко",
    "looking_at_robot": true,
    "emotion": "neutral"
  },
  "audio": {
    "speech": "Привет, робот",
    "lang": "ru"
  },
  "memory": ["в прошлый раз спрашивала про расписание"],
  "last_robot_action": null
}
```

### 5.2. Модель решения (выход)

```json
{
  "decision": "ACT",
  "confidence": 0.91,
  "speech": {"text": "Привет, Айгерим!", "lang": "ru"},
  "motion": {"pan": 15, "tilt": 0, "gesture": "nod"},
  "memory_write": "поздоровалась 12 августа"
}
```

Два поля отличают эту модель от существующих систем:

- **`decision`** со значениями `ACT` / `WAIT` / `OBSERVE` — робот может осознанно не действовать. Отсутствие этой возможности и есть определение реактивной системы.
- **`confidence`** — на нём строится калибруемый порог вмешательства, позволяющий настраивать баланс «своевременность против навязчивости» без переобучения.

Схема выхода компилируется в грамматику декодера.

### 5.3. Модель памяти

Эпизодическая память, ключом которой является идентификатор личности из FaceID. Запись производится самой моделью через поле `memory_write`; чтение — подстановкой релевантных эпизодов в поле `memory` модели ситуации.

### 5.4. Модель неявной обратной связи

После каждого действия робота открывается окно наблюдения 3–5 секунд, в котором фиксируется:

| Сигнал | Интерпретация |
|---|---|
| Сдвиг эмоции (нейтральная → улыбка) | положительный |
| Сдвиг эмоции (нейтральная → раздражение) | отрицательный |
| Продолжение диалога | положительный |
| Отворачивание, уход из кадра | отрицательный |
| Перебивание робота на полуслове | отрицательный |
| Повторный тот же вопрос | отрицательный (робот не понял) |

Сигналы агрегируются в скалярную оценку, действия ранжируются в пары «лучше / хуже», пары используются для DPO. Ручная разметка не требуется.

## 6. Данные

Все датасеты берутся **готовыми**. Собственная генерация данных не производится; выполняется только конвертация готовой разметки в схемы раздела 5.

### 6.1. Проактивность (ядро)

| Датасет | Объём | Роль |
|---|---|---|
| `thunlp/ProactiveAgent`, `dataset/reward_data` | 1 749 записей | Обучение решению «вмешаться или нет» |
| ProAgentBench | реальные данные | Внешний тестовый набор |
| When2Call (NVIDIA) | 15 000 (SFT) + 9 000 (пар) | Резерв для расширения корпуса |

**Уточнение по факту загрузки (2026-08-15).** Заявленные в статье 6 790 событий
ProactiveBench в репозитории **не опубликованы** — README указывает, что они
порождаются их собственным пайплайном (GYM) из трасс пользовательской
активности. Публично доступна только обучающая выборка их reward-модели:
1 749 записей.

Фактический выход после конвертации:

| Категория | Записей | Наша метка |
|---|---|---|
| Correct-Detection | 504 | ACT с текстом действия |
| False-Alarm | 943 | WAIT |
| Correct-Rejection | 179 | WAIT |
| Missed-Need | 123 | пропуск: нужен ACT, но текста действия нет |

Итого 1 626 примеров с балансом 31% ACT против 69% WAIT. После выравнивания
классов — **1 008 примеров**, что даёт потолок всего корпуса около 1 830.

Эталонная метка берётся из поля `category`, а не из `help_needed`: проверка
показала, что `help_needed` отражает суждение самого агента, и среди записей
с `help_needed=True` встречаются 244 штуки категории False-Alarm.

**Следствие для плана работ.** Объёма достаточно, чтобы обучить адаптер и
проверить весь пайплайн от начала до конца, но для итоговых экспериментов
корпус проактивности необходимо расширить. Варианты по возрастанию стоимости:
When2Call, конвертация HRI-корпусов из раздела 6.2, воспроизведение пайплайна
GYM. Этот пункт переходит в открытые вопросы.

Домен исходных данных — активность за компьютером, не робототехника. Это
превращается в **преимущество**: перенос из десктопного домена в воплощённый
является самостоятельным исследовательским вопросом и защищается сильнее, чем
обучение на самостоятельно сгенерированных данных.

### 6.2. Реакция человека → неявная награда

| Датасет | Что даёт |
|---|---|
| REACT | Два корпуса реакций людей на робота и оценочной обратной связи во времени |
| UE-HRI | 54 спонтанных взаимодействия (4–15 мин) с разметкой вовлечённости |
| eHRI database | Мультимодальная база вовлечённости в HRI |
| Vernissage corpus | 1 ч 29 мин, робот и несколько людей: взгляд, кивки, определение адресата |
| awesome-hri-datasets | Каталог для добора при необходимости |

Наличие этих корпусов позволяет обучить и провалидировать модель неявной награды **на опубликованных данных**. Эксперименты с участием людей и этическое одобрение смещаются на финальную проверку, что снимает главный риск проекта со старта.

### 6.3. Вызов команд и структурный вывод

`Salesforce/xlam-function-calling-60k`, `NousResearch/hermes-function-calling-v1`, `glaive-function-calling-v2`, ToolACE, `APIGen-MT-5k`, `BUTTONInstruct`, tau-bench train.

Оценка: **BFCL** (Berkeley Function-Calling Leaderboard), **τ-bench**.

### 6.4. Retention

`HuggingFaceH4/ultrachat_200k`, `oasst2`, русскоязычные инструкционные корпуса.

### 6.5. Состав обучающего микса

| Доля | Данные | Роль |
|---|---|---|
| 50% | ProactiveBench, When2Call (конвертированные) | проактивность |
| 20% | xLAM, Hermes, glaive, ToolACE | форма и точность команд |
| 25% | ultrachat, oasst2, русские корпуса | replay против забывания |
| 5% | примеры с меткой «отклонено» из ProactiveBench и When2Call | умение **не** реагировать |

Баланс `ACT` и `WAIT` в корпусе удерживается около 50/50. При перекосе в сторону `ACT` проактивность вырождается в навязчивость.

**Ограничение по объёму.** Проактивные данные — узкое место: после конвертации
и выравнивания классов их около **1 000 примеров**, что даёт полный корпус
порядка **1 800**. Следствия:

1. Остальные источники берутся не целиком, а выборкой пропорционально долям таблицы.
2. Для LoRA такого объёма хватает на рабочий адаптер и полную проверку пайплайна,
   но для итоговых экспериментов корпус нужно расширять новыми источниками
   проактивности, а не числом эпох на тех же примерах.
3. Расширение идёт за счёт When2Call и HRI-корпусов из раздела 6.2, а не за
   счёт дублирования имеющихся записей.

**Выравнивание классов обязательно.** В исходных данных WAIT встречается вдвое
чаще ACT. Без прореживания преобладающего класса модель приходит к вырожденной
стратегии «молчать всегда», которая даёт высокую формальную точность при полной
бесполезности. Прореживаем большинство, а не размножаем меньшинство:
дублирование редких положительных примеров ведёт к переобучению на них.

### 6.6. Разбиение данных

- **train / val** — конвертированные открытые корпуса
- **test** — ProAgentBench, HRI-корпуса, не использованные в обучении, и записи реальных взаимодействий с прототипом

Тестовые данные не должны происходить из того же источника, что обучающие: иначе измеряется совпадение с источником, а не качество агентности.

### 6.7. Конвертация

Ни один готовый датасет не представлен в схемах раздела 5. Требуется скрипт-адаптер, перекладывающий готовую разметку в модель ситуации и модель решения. Это конвертация, а не создание данных: новая разметка не производится, люди не привлекаются, генерация синтетики моделью-учителем не выполняется.

В диссертации описывается как методика приведения разнородных HRI-корпусов к единой информационной модели ситуации (пункт 4 научной новизны).

### Стек

- Обучение: LLaMA-Factory или Unsloth

- Инференс: vLLM (горячее переключение LoRA-адаптеров, структурированный вывод по грамматике)
- Резерв для слабого железа: llama.cpp с GBNF

## 8. Эксперименты

### 8.1. Бейзлайны

| № | Конфигурация | Что изолирует |
|---|---|---|
| 1 | Текущая система (облачный LLM-оркестратор) | прирост от локальности и обучения в целом |
| 2 | Qwen3-8B без адаптера, только промпт | вклад обучения отдельно от выбора модели |
| 3 | Qwen3-8B + адаптер, реактивный режим (без `WAIT`) | вклад проактивности |
| 4 | Полная система после DPO | вклад самообучения |

Каждый пункт научной новизны получает собственную строку в таблице результатов.

### 8.2. Метрики

**Агентность**
- доля своевременных вмешательств
- доля ложных вмешательств
- навязчивость: число вмешательств в минуту при отсутствии обращения

**Корректность**
- доля валидных команд (ожидается 100% благодаря грамматике — это проверка механизма, а не цель обучения)
- точность выбора действия

**Retention**
- качество диалога и точность tool-calling до и после обучения
- кривая компромисса «прирост агентности против потери общих способностей»

**Ресурсы**
- задержка принятия решения
- потребление VRAM
- стоимость эксплуатации (ноль против текущих затрат на токены)

## 9. Риски

| Риск | Вероятность | Способ снижения |
|---|---|---|
| Деградация речи при обучении адаптера | средняя | Разделение контуров + replay 25% + обязательный замер на этапах 0 и 6 |
| Перенос с десктопного домена на воплощённый не работает | средняя | Это исследовательский вопрос, а не только риск: отрицательный результат тоже публикуем. Резерв — добор HRI-корпусов |
| Модель награды научилась поощрять угодливость, а не пользу | средняя | Отдельная валидация модели награды на HRI-корпусах; контроль на удержание сценария, а не только на положительную эмоцию |
| Проактивность вырождается в навязчивость | высокая | Баланс `ACT`/`WAIT` 50/50, 5% негативных сцен, калибруемый порог на `confidence` |
| Обвинение в отсутствии новизны («это интеграция») | средняя | Формулировки раздела 3 подкрепляются обзором литературы (задача 1); четыре бейзлайна изолируют вклад каждого компонента |

## 10. Открытые вопросы

1. Требуется проверка условий доступа к HRI-корпусам (UE-HRI, eHRI, Vernissage, REACT) — часть выдаётся по запросу.
2. Точный порог качества казахского у чистого Qwen3-8B не замерен — влияет на решение о языковом адаптере на более позднем этапе.
3. Формулировки научной новизны требуют сверки с шаблоном, принятым в вузе, и подтверждения обзором литературы.
