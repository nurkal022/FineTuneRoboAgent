# Проактивная агентность вербального робота

Обучение LoRA-адаптера поверх замороженной LLM для проактивного управления
социальным роботом: робот сам решает, **когда** вмешаться, и дообучается на
неявной реакции человека без ручной разметки.

Дизайн и научная постановка: [docs/superpowers/specs/2026-08-12-llm-agency-design.md](docs/superpowers/specs/2026-08-12-llm-agency-design.md)

## Главное про архитектуру

Базовые веса модели **не изменяются никогда**. Обучается только LoRA-адаптер:

- **Контур решений** — база с включённым адаптером: `ACT / WAIT / OBSERVE`, команды, память
- **Речевой контур** — та же база с **выключенным** адаптером: говорит с человеком

Отсюда следует главное свойство: катастрофическое забывание речи структурно
невозможно, потому что речевой контур в обучении не участвует.

Валидность команд обеспечивается **грамматикой декодера**, а не обучением.
Невалидный JSON или угол серво вне диапазона непредставимы на уровне выбора
токена, независимо от того, как прошло обучение.

## Установка

```bash
python -m venv .venv && source .venv/bin/activate
pip install -e ".[train,dev]"     # обучение
pip install -e ".[serve]"         # инференс (vLLM), обычно отдельным окружением
```

### Бэкенд обучения: Unsloth или HF

Обучение работает на двух взаимозаменяемых бэкендах, переключается полем
`engine` в конфиге. Адаптер на выходе одинаковый.

| | `unsloth` | `hf` |
|---|---|---|
| VRAM | примерно вдвое меньше | базовое потребление |
| Скорость | примерно вдвое быстрее | базовая |
| GPU | **только один** (в бесплатной версии) | несколько |
| Устойчивость | патчит `transformers`/`trl`, чувствителен к их версиям | обычный стек |

Для 4090 (24 ГБ) Unsloth фактически обязателен, на A100 80 ГБ он даёт в
основном скорость. Ставится отдельной командой — pip должен сам подобрать
совместимые версии, а не разрешать конфликт вслепую:

```bash
pip install unsloth
```

Если Unsloth сломается на очередном обновлении — переключите `engine: hf`
в `configs/sft.yaml` и `configs/dpo.yaml`, и обучение пойдёт прежним путём.
Ради воспроизводимости экспериментов зафиксируйте версии (`pip freeze`)
в момент запуска финальной серии.

**Бэкенд DPO должен совпадать с бэкендом SFT** — адаптер дообучается тем же
стеком, которым обучался. Тест `test_shipped_configs_are_valid` это проверяет.

## Порядок работы

### Шаг 1. Сверить поля датасетов (обязательно перед первым запуском)

Имена колонок в открытых корпусах меняются между версиями. Автоопределение
работает по списку кандидатов, но проверить надо глазами:

```bash
robo-agency inspect-dataset thunlp/ProactiveAgent --split train
```

Если сопоставление промахнулось, пропишите поля явно в `configs/data_mix.yaml`:

```yaml
proactivity:
  - path: thunlp/ProactiveAgent
    field_map:
      observation: events
      action: task
      label: label
```

### Шаг 2. Собрать обучающий корпус

```bash
robo-agency build-data --config configs/data_mix.yaml --output data/processed
```

Команда напечатает отчёт о миксе. Обратите внимание на две строки:

- **баланс ACT/WAIT** — должен быть около 50/50, иначе робот получится навязчивым
- **ограничивающий источник** — почти наверняка проактивность; она же задаёт
  потолок размера всего корпуса (порядка 12–15 тысяч примеров)

Примеры никогда не дублируются: при запросе размера больше достижимого корпус
урезается, а не добивается повторами.

### Шаг 3. Замерить базу до обучения (этап 0)

```bash
robo-agency retention --base Qwen/Qwen3-8B --adapter <пусто-или-старый> \
  --eval-file data/processed/retention_eval.jsonl
```

Это точка отсчёта для главы про компромисс «агентность против речи».
BFCL и τ-bench запускаются отдельно своими штатными харнессами.

### Шаг 4. Обучить адаптер решений (этап 2)

```bash
robo-agency train-sft --config configs/sft.yaml
```

На A100 это часы, не дни. Если база не влезает в память — `load_in_4bit: true`
в конфиге.

### Шаг 5. Собрать пары предпочтений из логов эксплуатации (этап 4)

Лог взаимодействий — jsonl, по строке на действие робота:

```json
{
  "situation_key": "sess42-t17",
  "messages": [{"role": "system", "content": "..."}, {"role": "user", "content": "..."}],
  "decision_json": "{\"decision\":\"ACT\",...}",
  "reaction": {
    "emotion_before": "neutral",
    "emotion_after": "happy",
    "continued_dialogue": true,
    "left_frame": false,
    "engagement_seconds": 8.0
  }
}
```

```bash
robo-agency build-pairs --input logs/interactions.jsonl \
  --output data/processed/preference_pairs.jsonl
```

Пары строятся **только внутри одной ситуации**: награды из разных ситуаций
несравнимы. Пары с разницей награды меньше `--min-margin` отбрасываются — на
них DPO учит шум измерения эмоций.

### Шаг 6. DPO на неявной обратной связи (этап 5)

```bash
robo-agency train-dpo --config configs/dpo.yaml
```

### Шаг 7. Повторный замер retention (этап 6)

Та же команда, что на шаге 3, с новым адаптером. Рост NLL = речь начала
деградировать.

## Инференс

```python
from robo_agency.serve.controller import ControllerConfig, RoboController
from robo_agency.schema import Situation, Audio, Person

controller = RoboController(ControllerConfig(
    adapter_path="outputs/adapter-decisions-dpo",
    act_threshold=0.62,            # из калибровки, этап 3
))

outcome = controller.decide(Situation(
    silence_sec=4.0,
    person=Person(id="u_017", name="Айгерим", known=True, last_seen="3 дня назад"),
    audio=Audio(speech=None),
    memory=["в прошлый раз спрашивала про расписание"],
))
print(outcome.decision.decision, outcome.act_probability)
```

Решение принимается в два шага: сначала дешёвый ограниченный выбор из трёх
вариантов с логвероятностями (отсюда берётся калиброванная уверенность), и
только при прохождении порога — полная генерация по JSON-схеме. На WAIT-ситуациях,
а их около половины, дорогой шаг не выполняется вообще.

## Структура

```
src/robo_agency/
  schema.py              информационные модели ситуации и решения
  prompts.py             сборка примеров, единая для обучения и инференса
  data/
    fields.py            автоопределение колонок в готовых датасетах
    proactivity.py       ProactiveBench / When2Call → схема решений
    conversational.py    function-calling и replay → диалоговый формат
    mixer.py             микс в пропорциях, без дублирования
    build.py             полный цикл сборки корпуса
  training/backends.py   переключение бэкендов Unsloth / HF
  training/sft.py        этап 2
  training/dpo.py        этап 5
  reward/implicit.py     неявная награда, пары предпочтений
  evaluation/agency.py   своевременность, ложные вмешательства, навязчивость
  evaluation/calibration.py  порог вмешательства
  evaluation/retention.py    сохранение речи
  serve/controller.py    двухконтурный рантайм на vLLM
```

## Тесты

```bash
pytest -q
```

Покрыта логика, ошибка в которой тихо испортила бы обучение: инварианты схемы
решений, пропорции микса и запрет дублирования, построение пар предпочтений,
метрики агентности и калибровка порога.

## Что важно знать про данные

Function-calling и replay-корпуса намеренно **не** конвертируются в схему решений
робота — они остаются в родном диалоговом формате. Их задача сохранить у модели
то, что она уже умеет; перегонка в `RobotDecision` уничтожила бы ровно тот навык,
ради которого они добавлены.

К схеме `Situation` / `RobotDecision` приводятся только корпуса проактивности.
